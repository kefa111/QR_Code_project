Can it be fixed? The repair budget

13 bytes damaged, spread over 4 of 4 blocks. Every block is within its limit, so all of it can be rebuilt.

The bytes of a code are split into 4 blocks that are repaired separately. Each block can fix only a fixed number of wrong bytes (the line), and it counts bytes, not scratches: a byte with all 8 squares wrecked costs the same as a byte with one.

Each wrong byte costs two backup bytes: one to work out where it is, one to work out what it should be. So n backup bytes fix at most n/2 wrong bytes. Go past that and the maths usually notices and gives up. Very rarely it is fooled.

What this page simplifiesThe honest limits of the simulation
  • The repair maths is the real thing. The codes are built from scratch following the QR standard, and an independent decoder (OpenCV) reads every code this page produces. On damaged codes it never reads one that this page cannot.
  • The camera is simplified. A real phone must first find the code in a photo, using the three big corner squares, and then sample a grid. We assume the grid is found, except that we warn you when a corner square is badly damaged. Blur, glare, perspective and shadows are not simulated.
  • Damage is black and white flips. Some real scanners are cleverer and use how uncertain each square looks to repair even more.
  • Only byte mode is built. QR codes also have compact modes for digits, capital letters and Kanji. They change how the message is packed, not how repair works.
  • L, M, Q and H percentages are best cases. They describe damage packed into as few bytes as possible. The experiment shows what happens when it is not.
  • Test it for real: press "Save as image" under the code and scan the picture with your phone.

Everything here is computed in your browser by the code in the page source: no libraries, no network calls, no recorded results. The repair algorithm (Reed–Solomon over GF(256): Berlekamp–Massey, Chien search and Forney's formula) is written out in core.js.
